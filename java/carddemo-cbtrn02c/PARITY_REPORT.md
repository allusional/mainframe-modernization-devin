# CBTRN02C — COBOL vs Java functional parity report

Subject: `app/cbl/CBTRN02C.cbl` (job `POSTTRAN`, daily transaction posting) and its Java port
in `java/carddemo-cbtrn02c`.

Result: **all output records of both scenarios are byte identical**, as are the DISPLAY output,
the processed/rejected counters and the return code.

## 1. How the baseline was obtained

The COBOL baseline is produced from the **unmodified** `app/cbl/CBTRN02C.cbl` — the program is
compiled and executed, not simulated:

* Compiler/runtime: **GnuCOBOL 3.1.2** (`cobc`, Ubuntu package `gnucobol3`), indexed file
  handler BDB. No z/OS or Db2 is involved; there is no LE, so the `9999-ABEND-PROGRAM`
  path (`CALL 'CEE3ABD'`) is not reachable in this environment and is not exercised.
* `cobc -x -fsign=EBCDIC -I app/cpy`. **`-fsign=EBCDIC` is required**: the CardDemo datasets
  store signed `PIC S9(n)V99 DISPLAY` fields with the IBM overpunched trailing sign
  (`{`, `A`–`I` for +0..+9, `}`, `J`–`R` for -0..-9), whereas GnuCOBOL defaults to its own
  ASCII sign convention and silently misreads them (`5.25` becomes `5.20`, negatives become
  positive).
* The VSAM KSDS clusters (XREFFILE, ACCTFILE, TCATBALF, TRANFILE) are emulated by GnuCOBOL
  indexed files. Six small helper programs under `parity/cobol/` load the flat sample datasets
  into indexed files before the run (`LOADXREF`, `LOADACCT`, `LOADTCAT`) and dump the indexed
  outputs back to flat files in ascending key order afterwards (`DUMPTRAN`, `DUMPACCT`,
  `DUMPTCAT`). They only move bytes; no business logic lives in them.
* Driver: `parity/scripts/run_cobol.sh <scenario>`; outputs are committed under
  `parity/golden/<scenario>/` and are what the JUnit parity test asserts against, so the
  test suite runs on machines without a COBOL compiler.

The Java port reads and writes exactly the same flat files
(`parity/scripts/run_java.sh <scenario>`), driven by the same `DD_*` environment variables.

## 2. Inputs used

| Scenario | Inputs | Purpose |
| --- | --- | --- |
| `full` | `app/data/ASCII/{dailytran,cardxref,acctdata,tcatbal}.txt` — 300 daily transactions, 50 xref records, 50 accounts, 50 category balances | the datasets shipped with the repository |
| `branches` | `parity/data/branches/*` — 10 daily transactions, 5 xref records, 4 accounts, 2 category balances (generated by `parity/scripts/gen_branches_dataset.py`) | deliberately exercises every validation and update branch |

Records are fed to both programs as fixed length records with no delimiters
(`prep_inputs.sh`), which is the byte layout `ORGANIZATION SEQUENTIAL` expects.

## 3. Output record comparison

`ParityCompare` reads both sides as fixed length records and compares them byte for byte
(`parity/scripts/run_parity.sh`, and `CobolParityTest` in the build).

return code matches: 4

### Scenario `branches`

```
counters match: TRANSACTIONS PROCESSED :000000010 TRANSACTIONS REJECTED  :000000005
return code matches: 4
MATCH    TRANSACT.dat   5 records byte identical
MATCH    ACCTDATA.dat   4 records byte identical
MATCH    TCATBAL.dat    5 records byte identical
MATCH    DALYREJS.dat   5 records byte identical

```

The DISPLAY output also matches line for line, including every
`TCATBAL record not found for key : <key>.. Creating.` message and its position in the log
(50 such messages in `full`, 3 in `branches`).

The single field that cannot match is `TRAN-PROC-TS`: `Z-GET-DB2-FORMAT-TIMESTAMP` stamps it
from the machine clock, so the two runs necessarily differ. It is compared for format
(`EEEE-MM-DD-UU.MM.SS.HH0000`) instead of value; all other 324 bytes of every transaction
record are compared literally.

## 4. Per-branch coverage

| Paragraph / branch | Covered by | Verified outcome |
| --- | --- | --- |
| `1500-A-LOOKUP-XREF` INVALID KEY → reason 100 | `branches` tran 3 | reject trailer `0100INVALID CARD NUMBER FOUND` |
| `1500-B-LOOKUP-ACCT` INVALID KEY → reason 101 | `branches` tran 4 | reject trailer `0101ACCOUNT RECORD NOT FOUND` |
| credit limit exceeded → reason 102 | `branches` tran 5, all 38 rejects of `full` | reject trailer `0102OVERLIMIT TRANSACTION` |
| transaction after expiration → reason 103 | `branches` tran 6 | reject trailer `0103TRANSACTION RECEIVED AFTER ACCT EXPIRATION` |
| both 102 and 103 apply (order dependence) | `branches` tran 7 | 103 overwrites 102, as in the COBOL |
| boundary `ACCT-CREDIT-LIMIT >= WS-TEMP-BAL` | `branches` trans 5 (100.01, rejected) and 8 (100.00, posted) | limit is inclusive |
| `2700-A-CREATE-TCATBAL-REC` (key missing) | `branches` trans 2, 8, 10; 50 keys in `full` | new record, balance = amount, FILLER carried over |
| `2700-B-UPDATE-TCATBAL-REC` (key present) | `branches` trans 1 and 9 (25.00 → 130.25) | balance accumulates |
| `2800` credit path (`DALYTRAN-AMT >= 0`) | `branches` trans 1, 8, 9, 10 (incl. a 0.00 amount) | `ACCT-CURR-CYC-CREDIT` increased |
| `2800` debit path (`DALYTRAN-AMT < 0`) | `branches` tran 2 | `ACCT-CURR-CYC-DEBIT` increased by the negative amount |
| `2900-WRITE-TRANSACTION-FILE` | every accepted transaction | 262 / 5 records written |
| `2500-WRITE-REJECT-REC` layout | every reject | 350 byte daily record copied verbatim + 80 byte trailer |
| `RETURN-CODE 4` when rejects exist | both scenarios | exit code 4 on both sides |
| `RETURN-CODE 0` when nothing is rejected | not covered — every shipped and crafted dataset produces at least one reject | logic asserted by unit test only |
| `9999-ABEND-PROGRAM` / file status error paths | not covered — no LE runtime, and the flat/indexed files cannot produce the corresponding VSAM statuses | see caveats |

## 5. Behaviours that had to be reproduced exactly

1. **Overpunched signs.** All money fields are re-encoded on output with the IBM overpunch,
   so an input value written as `00000000000` comes back as `0000000000{`.
2. **`INITIALIZE` does not clear `FILLER`.** `2700-A-CREATE-TCATBAL-REC` initialises
   `TRAN-CAT-BAL-RECORD` and writes it, but the 22 byte FILLER keeps whatever the previous
   `READ ... INTO` left in working storage. In the `full` dataset that is `0` characters
   (the existing records are zero filled), in `branches` it is spaces. The port therefore
   keeps a persistent working-storage record and resets only the named items.
3. **Validation order.** The expiration check runs even when the credit limit check already
   failed, so reason 103 overwrites 102.
4. **Rejects are raw bytes.** `MOVE DALYTRAN-RECORD TO REJECT-TRAN-DATA` is a group move: the
   reject record contains the input record unmodified (not re-encoded), plus the 80 byte
   trailer of `9(4)` reason code and `X(76)` description.
5. **`TRANFILE` is opened `OUTPUT`**, so the transaction master is recreated by every run and
   contains only the transactions posted by that run.

## 6. Data defect found (not fixed)

`app/data/ASCII/tcatbal.txt` is stored with **CRLF line endings** while every other dataset in
that directory uses LF. Loaded verbatim, its 50 byte records become 51 bytes and the whole file
shifts out of alignment — with the raw file the COBOL run itself mis-keys every category
balance and reports 43 rejects instead of 38. The harness strips the CR
(`prep_inputs.sh`) for both implementations rather than changing the dataset. Flagging it here:
the file should probably be normalised to LF in the repository.

## 7. Environment caveats

* GnuCOBOL is not z/OS Enterprise COBOL. Arithmetic on `DISPLAY` and `COMP-3` operands and the
  record layouts are identical for this program's picture clauses, but a run on z/OS may still
  differ in areas this program does not use (e.g. `CALL 'CEE3ABD'`, VSAM specific file status
  values, EBCDIC collation of the indexed keys). Records here are ASCII; on the mainframe the
  same layouts are EBCDIC, and key ordering for the alphanumeric `TRAN-ID`/`XREF-CARD-NUM` keys
  can differ if keys ever mix digits with letters. All keys in the shipped data are numeric,
  where ASCII and EBCDIC order agree.
* The abend and I/O error paths are unreachable in the harness, so they are ported by
  inspection rather than proven by comparison.
* Concurrency, CICS and Db2 are not involved in this batch program.

## 8. Reproducing

```bash
sudo apt-get install -y gnucobol3
cd java/carddemo-cbtrn02c
./parity/scripts/run_parity.sh          # COBOL baseline + Java run + byte comparison
mvn verify                              # 30 tests, incl. the golden parity gate
```
